- Every text in [src/locales]/<lang>/*.json, with keys that say
  where the text appears (home.hero.title, not text1)
- A short TEXTS.md that says which file and key holds which part of

At the end, show me TEXTS.md.

What your agent does

  1. Moves every text into one JSON file per language under src/locales, with keys that say where the text appears (home.hero.title, not text1), so a person who does not code finds it.
  2. Writes TEXTS.md: which file and key holds which part of which page, and how to change a line on GitHub in the browser.
  3. Adds npx i18next-cli status before the build, so a missing translation stops the deploy instead of reaching the site.
  4. Shows you TEXTS.md at the end, so you can check it before you hand it over.

Two ways to change a text

The client edits the file

The texts are JSON files in the repository. Your client opens the file on GitHub, changes the line with the pencil icon and saves; the build checks every language and deploys. Or they send you the change and your agent makes it. This costs nothing extra and fits when changes are rare or when you want to look at each one.

Your client changes the texts in a web editor, in every language, without the repository. A webhook can start a new build of the site when texts change or a version is published, or the site loads the published texts from the Locize CDN, so a change shows without a deploy. It fits when the client changes texts often or on their own schedule, and when you look after many client sites. Your agent connects the existing files with npx i18next-cli locize-migrate (it needs locize-cli and a project ID and API key).

Before you hand it over

  • Change one text the way your client will, and watch it reach the site.
  • Agree who reads a change in the other languages: a client fixing the English does not fix the German. Keep every language current shows how.
